 1) Daily Maximum Pairs (5)

This is only a payout limit.

Meaning:

Even if the user has 50 pairs possible today, you will pay only 5 pairs today.

The remaining pairs are not lost — they stay as unused BV.

So Daily Max Pairs controls: “How much pair commission can be paid per day.”

2) Carry Forward Mode (daily / weekly / lifetime)

This controls: “How long unused BV can remain valid.”

Because when Daily Max Pairs blocks payout, you will have leftover BV.

Carry Forward Mode decides what happens to that leftover BV:

✅ lifetime

Unused BV never expires.

Tomorrow you can still use it to make pairs.

✅ daily

At end of day, leftover BV is reset to 0 (or flushed).

Tomorrow starts fresh (no carry).

✅ weekly

Carry allowed within the same week.

When week changes, leftover BV reset.

So Carry Forward Mode is about expiry/reset, not payout speed.

3) Carry Forward Cap (BV)

This controls: “Maximum BV allowed to carry forward.”

Example:

Carry cap = 50,000 BV

If left has 90,000 BV leftover, system keeps only 50,000, and extra 40,000 is discarded (or frozen).

Why? To prevent very old users from stacking unlimited BV and breaking payouts later.

## Recommended architecture for BMAN

For your staking platform, I recommend:

- **Users deposit USDT (BEP-20) only**.
- **Platform detects deposits automatically using BscScan/RPC**.
- **Backend credits the user's internal Exchange Wallet** according to the configured exchange rate.
- **When needed, the backend transfers BMAN from the Treasury Wallet by signing transactions with the Treasury private key stored securely on the server**.
- **Users never see or control the Treasury private key**, and they do not need individual BMAN private keys unless you intentionally build a fully non-custodial system.

This architecture is simpler, more secure, and aligns well with how most centralized staking and MLM platforms operate.

# Security

- Generate one custodial BSC wallet per user at registration.
- Encrypt the user's private key using AES-256 with a server-side master key stored outside the database (e.g., in environment configuration or a secure secret manager).
- Never display or expose the private key or recovery phrase in the UI.
- Require Email OTP and Transfer Password for withdrawals.
- Verify KYC approval before allowing withdrawals.
- Use row-level locking/transactions when crediting balances to prevent duplicate credits.
- Prevent double-crediting by enforcing a unique constraint on `tx_hash`.
